### 1. 目标与范围

- 支持最小可用的三语言版本：
    - 简体中文（zh_CN）
    - 英文（en）
    - 繁体中文（zh_TW）
- 覆盖范围：
    - UI 文本（按钮、提示、结算文案）
    - 弹窗与系统提示
    - 可配置的关卡与目标描述（如 Objective 文案）
- 不在范围：
    - 字体资产与字形覆盖的细节优化（可后续单独扩展）

### 2. 基本策略（推荐方案）

- 使用 Godot 官方本地化体系。
- 文本统一通过“翻译 Key”间接获取，不在脚本或场景中硬编码显示文本。
- 翻译资源建议使用 **POT/PO**（便于专业翻译流程），也允许 CSV（小规模可用）。

### 3. 翻译资源与文件规范

#### 3.1 文件类型

- **POT**：模板，包含所有需要翻译的 msgid（Key）。
- **PO**：具体语言翻译文件，例如：
    - zh_CN.po
    - en.po
    - zh_TW.po

#### 3.2 Key（msgid）规范

- Key 必须稳定、语义清晰、可复用。
- 推荐格式：`域_模块_含义`，全部大写，使用下划线分隔。
    - 例：
        - MENU_START
        - MENU_SETTINGS
        - LEVEL_CLEAR
        - UNLOCK_SEASON_CONFIRM_TITLE
        - UNLOCK_SEASON_CONFIRM_BODY
- 禁止把“中文原文”直接作为 Key（会导致维护成本高，难以全局搜索与复用）。

#### 3.3 动态参数与格式化

- 动态文本必须支持插值参数（如星星数量、关卡编号）。
- 规范：插值参数的命名需要一致，例如 `{stars}`、`{season_name}`。
- 多语言格式化注意：
    - 英文可能需要复数形式（1 star vs 2 stars）
    - 中文通常不需要复数变化，但仍要保证语义完整

### 4. 语言选择与切换规则

#### 4.1 默认语言

- 首次启动：
    - 优先读取系统语言（Locale）
    - 若系统语言不在支持列表中，则回退到英文（en）或简体中文（按项目定位二选一）

#### 4.2 用户手动切换

- 游戏设置中提供语言选项。
- 用户选择后：
    - 立即生效
    - 写入存档/设置
    - 下次启动优先使用用户选择，而不是系统语言

#### 4.3 UI 刷新约束

- 语言切换后，所有显示文本应同步刷新。
- 对于运行时动态生成的 UI（例如选关列表、弹窗），必须在生成时读取当前语言文本。

### 5. 工程落地约束（实现口径）

- 项目设置中维护“支持语言列表”与“翻译资源列表”。
- 所有 UI 文本获取必须走翻译 Key：
    - 场景中的 Label/Button
    - 弹窗标题与正文
    - 关卡目标描述（如 Objective.description）
- 关卡配置中的文本字段建议存 Key，而不是存最终显示文案（方便统一翻译）。

### 6. 测试与验收标准（Acceptance Criteria）

1. 三种语言均可正常切换，且切换后 UI 文本即时更新。
2. 任意页面不存在“未翻译 Key”（例如直接显示 MENU_START 这类 Key）。
3. 缺失翻译时有明确回退策略（例如回退英文），不会出现空字符串或崩溃。
4. 含参数的文本在三语言下显示正确，数字与单位语序正确。
5. 用户选择语言会被持久化，重启后保持不变。

### 7. 备注与后续扩展

- 字体与字符集：如果后续引入像素字体，需要检查中英繁字符覆盖范围，并制定字体回退策略。
- 文案一致性：建议在后续建立一页“文案 Key 清单”，用于统一命名与避免重复。
