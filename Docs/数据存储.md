### 1. 目标与范围

- 目标：提供一套在 Godot 中可复用的“**数据 → 序列化 → 文件 → 恢复**”方案，满足：
    - **稳定**：断电/写入失败不应轻易损坏唯一存档。
    - **可演进**：数据结构升级时可兼容旧存档。
    - **可扩展**：新增系统（关卡、背包、设置）无需重写存档底层。
    - **可调试**：能快速定位缺失字段、版本不匹配等问题。
- 覆盖范围：
    - 玩家数据结构与模块化组织
    - 序列化/反序列化规则
    - 存档读写与备份
    - 存档触发策略（手动/事件/可选自动）
    - 道具数据：编辑器工具表与运行时数据库的分工

### 2. 分层架构（推荐）

> 原则：工具层与项目层分离；静态配置与玩家进度分离。
> 

#### 2.1 工具层（可跨项目复用）

- **GameSave（base_game_save）**
    - 职责：把“纯数据字典”写入/读取文件（例如 ConfigFile + 加密）。
    - 不关心业务字段。
- **BasePlayerData（base_player_data）**
    - 职责：
        - 提供模块化数据容器
        - 提供统一 `to_dict()` 序列化出口（递归处理字典/数组/可序列化对象）
        - 提供 `from_dict()` 入口（把数据装回容器）
    - 不关心具体模块含义。

#### 2.2 项目层（与游戏业务绑定）

- **PlayerData（运行时单例）**
    - 职责：
        - 管理“运行时可用的结构/实例”（例如 InventoryManager、ProgressionManager）
        - 提供 `to_dict()/from_dict()`，把运行时结构压缩为可存储的纯数据
- **SaveManager（运行时单例）**
    - 职责：
        - 管理“什么时候存、存到哪里、存档槽位、备份策略”
        - 监听 GameEvent 的存档信号

#### 2.3 编辑器工具与运行时数据库

- **ItemLibrary（编辑器工具 Resource）**
    - 职责：扫描资源目录，生成道具总表（供运行时使用）。
- **ItemDatabase（运行时单例）**
    - 职责：提供按 item_id 查询 ItemData 的能力。
    - 玩家存档只保存 item_id 与数量/实例数据，避免冗余。

### 3. 数据契约（Data Contract）

#### 3.1 模块化数据结构

- 玩家数据建议按模块划分（Profile / Inventory / Progression / Settings 等）。
- 模块的默认结构应在“新建存档”时统一初始化。

#### 3.2 纯数据要求

- 写入文件的数据必须是“纯数据”（Dictionary/Array/标量），不应包含 Node 引用、信号连接等运行时状态。
- 自定义对象若需要保存，必须提供可序列化表示（例如 `to_dict()` 输出）。

#### 3.3 版本号与迁移（建议）

- 存档根节点建议包含：
    - `save_version`
    - `created_at` / `last_saved_at`
- 加载时若版本不一致：
    - 执行迁移（补字段/改结构）
    - 或回退到默认值并记录日志

### 4. 序列化与反序列化策略

#### 4.1 序列化（to_dict）规则

- 递归处理：
    - Dictionary：逐项递归
    - Array：逐项递归
    - 具备 `to_dict()` 的对象：调用后继续递归
    - 标量：直接写入
- 关键约束：
    - 不存临时态（例如本局临时缓存、运行时 UI 状态）
    - 不存可从配置推导的数据（例如道具静态属性）

#### 4.2 反序列化（from_dict）规则

- 先装载纯数据到运行时结构，再由各模块负责“复活实例”。
- 对缺失字段：
    - 使用默认值补齐，保持旧存档可用。

### 5. 存档文件与备份策略

#### 5.1 路径与权限

- 强制使用 `user://` 作为存档目录，避免权限与安全风险。
- 启动时确保存档目录存在（必要时创建）。

#### 5.2 备份机制（推荐）

- 保存前如果目标文件存在：先复制为备份（例如 `.back` 或轮换备份 `.back1/.back2`）。
- 若保存失败或加载失败：可尝试回退到备份文件。

#### 5.3 多存档槽位（可选）

- SaveManager 管理 slot → path 映射。
- UI 层只负责选择 slot，读写统一走 SaveManager。

### 6. 存档触发策略（Save Policy）

#### 6.1 必须支持的触发点（建议）

- 关卡结算（成功/失败）
- 章节解锁（Season 解锁）
- 设置变更（语言、音量等）
- 退出游戏

#### 6.2 自动存档（可选）

- 若开启定时自动存档：
    - 必须依赖“游戏状态”判断安全时机（避免战斗/弹窗/加载中写盘）。
    - 自动存档应当可开关。

### 7. 道具数据的存储策略（Inventory）

- 可堆叠物品：存 `{item_id: quantity}`。
- 不可堆叠物品：存实例数组（每个实例包含 instance_id + 必要的动态属性）。
- 运行时展示与计算：通过 ItemDatabase 用 item_id 查静态数据。

### 8. 常见风险与规避

- **首次启动无存档**：加载应返回空数据并触发“新玩家初始化”。
- **写入中断导致损坏**：使用备份与（可选）临时文件策略。
- **把运行时对象写入存档**：严格限制只写纯数据。
- **信号误连导致重复保存**：存档信号要与保存目标一一对应。

### 9. 验收标准（Acceptance Criteria）

1. 无存档首次启动：能够自动初始化默认数据并正常进入游戏。
2. 保存后重启：数据完整恢复，关键字段一致（关卡、星星、背包）。
3. 新增模块/字段后：旧存档仍可加载，缺失字段有默认值。
4. 存档文件损坏时：可从备份恢复到最近一次可用状态。
5. 运行中高频触发存档信号：不会出现明显卡顿峰值（必要时通过策略限流）。
